# Draft Queue (Wish List) — Design

Date: 2026-08-15
Status: Approved, ready for implementation planning

## Problem

The board answers "who is the best pick right now" but nothing lets you plan
ahead. During a live draft the useful thinking happens between your picks, when
there is time; the clock is when there is none. Today that planning has nowhere
to live, so it happens in your head or on paper and gets re-derived every round.

## Goals

- Let a user build an ordered list of players they intend to draft.
- Keep that plan visible and current during the draft without manual upkeep:
  players taken by anyone should strike themselves off.
- Surface, rather than resolve, the moments when the plan disagrees with roster
  need — the user decides.
- Survive the two things that routinely destroy draft-day state: a CSV
  re-import and a Reset Draft.

## Non-goals

- No automatic drafting. The queue never picks for you.
- No change to the scoring in `js/recommend.js`. The queue does not add a third
  weight alongside `STARTER_BONUS` and `FLEX_BONUS`.
- No drag-and-drop. It cannot be done well with the native HTML5 API without a
  separate pointer-event path for touch, and this tool is used on a phone.
- No sharing or syncing queues between users.

## Decisions

### An ordered queue, not a set of favorites

Rejected: starred favorites, and tiered buckets. Both narrow the board without
telling you what to do on the clock, which is the moment the feature exists to
serve. Tiers additionally overlap the CSV's existing tier column.

### The queue is primary; scoring annotates it

Rejected: feeding a queue bonus into `score = rank - bonus`. That would override
the user's explicit ordering with arithmetic they would have to reason about
under a pick clock, and would add a third tunable weight to calibrate.

Instead the queue keeps the user's order, and each entry carries the same WHY
badge the board shows. When the plan and the roster disagree, the app says so
and names the alternative. The user decides.

### Identity is the normalized player name

Player ids are regenerated by `setPlayers` on every CSV re-import, so an
id-keyed queue would silently empty itself the morning of the draft — exactly
when a user refreshes their rankings. Normalized names survive that.

Reuses `normalizeName` from `js/sleeper.js` rather than introducing a second
notion of player identity. This inherits that function's known limitation: two
players whose names normalize alike collide. Documented, narrow, and consistent
with how Sleeper pick matching already behaves.

### The queue lives in `settings`

`settings.wishlist: string[]`, default `[]`. This places it inside the existing
`load()` settings merge, so it persists across reloads and is preserved by
`resetDraft()` — which is the correct behavior: a reset clears what happened,
not what you planned. `resetAll()` clears it, as it clears everything.

## Architecture

A new pure module, `js/queue.js`, mirroring how `js/recommend.js` is structured
— no DOM, fully testable under Node:

```
queueAdd(list, name)                     -> new list (no-op if already present)
queueRemove(list, name)                  -> new list
queueMove(list, name, delta)             -> new list (clamped at both ends)
resolveQueue(list, players, myTeamId)    -> entry[]
```

`resolveQueue` joins each queued name to a live player by normalized name and
returns, per entry: `{ name, player, taken, takenByMe, missing }`.

Three entry states:
- **available** — on the board, undrafted.
- **taken** — drafted by anyone; rendered struck through.
- **missing** — queued but absent from the current board. Occurs after a CSV
  re-import that no longer lists the player. Shown explicitly rather than
  dropped, so the user is never silently missing part of their plan.

All list mutations return new arrays; the UI writes them back via
`St.updateSettings({ wishlist: next })`. No new mutators are added to
`js/state.js`.

## UI

- A `☆` / `★` toggle on each board row in `PlayersTable`, appending to or
  removing from the queue.
- A new `QueuePanel` component at the top of the sidebar, above My Team, since
  it is the panel the user acts on.
- Each entry: position number, name, WHY badge (for available entries), and
  `↑` `↓` `✕` controls.

Reordering is by arrow buttons. Rejected drag-and-drop (native HTML5 DnD does
not work on touch without a separate pointer-event implementation, and this
tool is used on a phone) and numeric position inputs (clumsiest of the three
under a clock).

### The nudge

`QueuePanel` calls `scorePlayer` from `js/recommend.js` for available entries to
obtain each one's reason. A warning line renders only when it is actually
informative:

- the top available entry's reason is `BENCH` or `WAIT`, **and**
- some later available entry has a `FILLS …` reason.

It then names both — the queued pick and the alternative that fills a slot.
Deliberately silent otherwise; a warning that fires constantly is one the user
learns to ignore during the exact minutes it matters.

## Interaction with existing behavior

| Event | Effect on the queue |
| --- | --- |
| A player is drafted by anyone (manual or Sleeper sync) | Entry strikes through automatically — it derives from `player.drafted`, no wiring needed |
| Reset Draft | Queue survives (it is in `settings`) |
| Reset Everything | Queue cleared |
| CSV re-import | Queue survives; players absent from the new board show as `missing` |
| Undo a pick | Entry returns to available, same derivation |

## Error handling

- Empty queue — panel renders a short hint rather than an empty box.
- No rankings imported — every entry is `missing`; the panel says so.
- A player queued twice — impossible; `queueAdd` is a no-op when present.
- `queueMove` at either end — clamped, no error.
- No team selected — entries render without WHY badges and the nudge is
  suppressed, matching how the board already degrades.

## Testing

`js/queue.js` is pure, so it is covered by the existing Node runner with no new
dependencies. Cases:

1. Add appends; adding a present name is a no-op.
2. Remove is a no-op for an absent name.
3. Move clamps at first and last position; moving an absent name is a no-op.
4. `resolveQueue` classifies available, taken, taken-by-me, and missing.
5. `resolveQueue` matches on normalized names, so a re-imported board with
   differently-formatted names still resolves.
6. Order is preserved through every operation.

The nudge condition is logic worth its own coverage: assert it fires when the
top available entry is bench depth and a later one fills a slot, and that it
stays silent when the top entry already fills a slot.

## Consequence: the DOM-diff harness should be retired

`tools/dom-diff.mjs` asserts that `main` renders identically to the pre-rewrite
commit. That was the point during the port, and it earned its keep — it caught
thirteen dropped element attributes.

A new panel is DOM the baseline does not contain, so from this feature onward
the harness either accumulates a permanent exception list or reports noise.
Recommendation: retire `tools/dom-diff.mjs` once this feature lands, and decide
separately whether `tools/screenshot-diff.mjs` is worth keeping for future
visual checks. Deleting either is a separate, explicitly confirmed step — not
something this feature's implementation does silently.
